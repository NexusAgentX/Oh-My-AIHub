# 小圈子试用 Runbook

Feature #22 交付的受邀试用流程。系统的 `/admin/ops`“试用证据摘要”只聚合真实事实（计数、时间、状态）；它不能证明参与者是真人、渠道是真实充值所得或人民币已到账——这些判断由维护者与参与者完成。

## 准备

1. 按部署 Runbook 上线实例，完成管理员创建与首次改密。
2. 受邀账户由管理员创建并线下交付一次性初始凭据；参与者首次登录必须改密。
3. 与参与者约定平台外的沟通与反馈渠道（不进入本仓库）。

## 试用脚本（与 Issue 验收项一一对应）

1. **共享渠道**：至少 1 名非管理员参与者在中转站充值后配置自己的渠道，添加模型报价并通过真实验证。
2. **发起调用**：至少 3 名不同参与者用各自平台 Key 在官方 SDK 或兼容客户端中完成调用（四类原生入口均可）。
3. **优先级与回退**：同一 Key 的同一“模型 + API 格式”池配置两个真实渠道，观察一次首选成功与一次首选提交前失败后次选成功（调用记录的尝试序列可复核）。
4. **产生收入**：其他消费者的成功调用为共享者带来看得见的积分收入（共享者钱包与运营总览的“来自其他消费者”）。
5. **C2C 部分成交**：共享者用上述收入发布卖单，数量大于单笔成交量；另一参与者部分承接，完成付款声明与卖家放行；双方在平台外确认人民币结果。
6. **巡检窗口**：从首个真实调用前开始观察，直至部分成交完成后；期间 `/admin/ops` 巡检历史应全部通过、无不可解释差异。

## 证据收集（管理员）

- 每个阶段在“试用证据摘要”记录一次快照（计数与时间是系统事实，直接抄录即可）。
- 需要下钻细节时用固定路径：调用→尝试→结算→账本；C2C→挂单→交易→持有事件。
- 不收集、不外传：渠道 Base URL、上游 Key、平台 Key 明文、付款截图、联系方式原文、可识别的参与者反馈原文。

## 维护者判断（人类检查点）

- 逐项核对上述脚本的事实是否成立；确认外部人民币由双方线下核实。
- 汇总脱敏反馈后，由维护者明确决定：继续 / 调整 / 停止。
- 结论与脱敏证据写回 Issue（#22 与 Epic #16 的 Validated 条件），本 Runbook 不代替该判断。

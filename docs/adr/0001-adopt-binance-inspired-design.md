# ADR-0001：采用 Binance 风格设计语言

- 状态：已取代
- 已由：[ADR-0004：原样采用 Airtable 设计分析规范](0004-adopt-airtable-design-analysis.md) 取代
- 日期：2026-09-01
- 决策者：项目维护者
- 关联内容：Issue #2、`DESIGN.md`

## 背景

项目已经具备前后端工程骨架，但产品视觉语言尚未定义。用户明确要求后续采用 Binance 风格的 `DESIGN.md`。公开的第三方 Binance 设计分析提供了颜色、排版、间距、组件和响应式规则，但它不是 Binance 官方规范，且包含不可直接假定可用的定制字体和品牌表达。

需要建立一份属于 Oh-My-AIHub、能够被人类和 Agent 直接执行的视觉规范，同时明确来源、许可和品牌边界。

## 决策目标

- 为后续 UI 工作提供单一、可执行的设计事实来源。
- 保留 Binance 风格的黑黄对比、高信息密度、金融数字排版和涨跌语义。
- 满足中文文档、响应式、无障碍和 Agent 可读要求。
- 避免将第三方分析误认为官方规范，避免依赖币安商标和定制字体。

本决策不定义产品功能，也不要求立即重写当前前端页面。

## 候选方案

### 方案一：原样复制第三方文档

优点是内容完整、落地快速；缺点是英文内容与仓库规范不一致，并包含币安品牌表达、定制字体假设和当前项目不需要的交易页面细节。

### 方案二：建立中文项目化改编版

保留经过公开页面分析得到的核心 Token 和设计原则，用开源字体替代定制字体，补充无障碍、品牌边界和项目维护规则。内容更符合当前项目，也能作为后续实现的规范性来源。

### 方案三：继续使用中性默认风格

实现成本最低，但无法满足用户明确指定的视觉方向，也会让不同 Agent 继续生成不一致的界面。

## 决定

采用方案二。在仓库根目录维护中文 `DESIGN.md`，以 Binance 风格为参考建立 Oh-My-AIHub 自身的设计系统。

后续所有视觉、页面和组件任务必须先阅读 `DESIGN.md`。设计 Token、组件规则、响应式和无障碍要求以该文件为准。文档明确声明第三方来源和 MIT 许可，不使用币安 Logo、口号或定制字体资产。

## 后果

### 正面影响

- 人类与 Agent 获得统一、可执行的视觉约束。
- 颜色、排版、间距和组件状态可以逐步沉淀成代码 Token。
- 黑黄金融平台风格能够在不同页面保持一致。
- 品牌、许可和字体使用边界得到明确记录。

### 负面影响与成本

- 当前前端尚未完全实现新规范，后续需要通过独立 Issue 渐进收敛。
- 设计语言与 Binance 风格相近，需要持续避免品牌混淆和机械复刻。
- Token 变更需要同时维护文档与实现。

### 风险与缓解措施

- 品牌混淆：使用 Oh-My-AIHub 自有名称和资产，在文档中保留非官方声明。
- 字体授权：使用 Inter、IBM Plex Sans 与系统字体，不分发 Binance 定制字体。
- 可访问性不足：将 WCAG 2.2 AA、非颜色编码、键盘焦点和降低动效写入强制规则。
- 过度模仿：以设计原则和语义 Token 为约束，不复制具体页面、文案或品牌组件。

## 验证方式

- `DESIGN.md` 包含机器可读 Token 和完整中文规则。
- `AGENTS.md` 要求所有 UI 工作先读取 `DESIGN.md`。
- 后续 UI Issue 的 Acceptance 包含视觉一致性、响应式和无障碍验证。
- 实现中的颜色、字体、间距和组件状态可以追溯到 `DESIGN.md` Token。

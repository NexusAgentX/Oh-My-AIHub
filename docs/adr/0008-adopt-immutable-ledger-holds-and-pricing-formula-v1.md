# ADR-0008：采用不可变账本、双持有投影与计价公式 v1

- 状态：已通过
- 日期：2026-09-02
- 决策者：仓库维护者
- 关联内容：[Feature #18](https://github.com/NexusAgentX/Oh-My-AIHub/issues/18)、[Feature #20](https://github.com/NexusAgentX/Oh-My-AIHub/issues/20)、[ADR-0005](0005-adopt-centralized-zero-sum-ledger.md)、[ADR-0006](0006-adopt-postgresql-goose-and-fixed-point-amounts.md)

## 背景

ADR-0005 已确定中心化零和复式账本，ADR-0006 已确定九位定点存储，但还需要固定可执行的不变量：如何保存历史、如何表达 API 预授权与 C2C 卖单冻结、信用冻结和超限如何影响可消费额度，以及后续代理结算如何从模型基准价、倍率和手续费得到确定金额。若这些语义只存在于调用方，重复请求、并发操作或未来 Feature 很容易产生不同结果。

## 决策目标

- 任意余额变化都有平衡、可追溯且不可原地修改的来源记录。
- API 消费授权和 C2C 资产冻结共享原子基础，但不能混淆各自可用资金规则。
- 幂等重放返回首次结果快照，异载荷复用同一键明确冲突。
- 信用冻结、信用超限和系统账户具有单一、可计算的领域语义。
- Feature #20 可以用同一公式得到跨平台可复算的提供者收入与平台手续费。

本决策不定义渠道路由、平台代理协议、C2C 订单状态机或人民币付款流程。

## 候选方案

### 方案一：只保存可变余额与业务订单

实现较少，但无法可靠回答每一笔积分从何而来，也难以抵抗重复结算、部分失败和后台直接改余额。

### 方案二：不可变分录、显式持有事件、数据库投影与公式 v1

余额由有序平衡分录形成；冻结由持有及不可变事件形成；数据库保存高效投影并在事务提交时复算验证；所有命令保存幂等结果快照；价格公式固定任意精度中间运算和向上取整顺序。

### 方案三：事件流作为唯一运行时读取模型

审计能力强，但每次读取需要完整折叠事件或额外异步投影，给首版增加不必要的基础设施与一致性延迟。

## 决定

采用方案二。

- 每个身份拥有唯一用户账本账户；平台激励账户和平台损失账户各有且只有一个。所有账户的已入账余额总和始终为零。
- 交易至少包含两条有序、非零、金额平衡的分录。交易封存后及分录写入后不可修改或删除；纠错只能创建对原交易逐条精确取反的冲正。
- 账户保存 `posted_balance`、`asset_reserved` 和 `spend_authorized` 三个同步投影。C2C 卖单使用仅允许正余额支持的资产冻结；API 请求使用允许信用额度支持的消费授权。两类持有只为正金额创建，支持部分 capture 与 release，capture 交易必须与唯一持有事件、同一命令和同一源借记原子对应。
- 有效信用额度在信用冻结时为零；由于冻结阻止所有新的借记和持有，冻结账户对外展示的可操作额度也固定为零。未冻结时 `spendable = max(posted + effective_credit - asset_reserved - spend_authorized, 0)`；`credit_used = max(-posted, 0)`；仅当 `credit_used > effective_credit` 时为信用超限。已经存在的持有仍可完成或释放。
- 管理员调整必须有明确对手方、操作者、原因和业务引用；坏账只把既有用户负余额转移到平台损失账户。普通浏览器用户不能直接提交通用账本交易。
- 幂等键按操作命名空间隔离。首次成功结果以快照保存并永久重放；相同键和不同载荷冲突；任何未完成命令不得提交。
- 计价公式 v1 使用任意精度整数完成中间运算，最后校验九位定点范围。四类 token 用量与对应每百万 token 基准价先求和，再乘渠道倍率并整体向上取整为提供者金额；平台手续费再对提供者金额按费率独立向上取整。自有渠道调用同时保留消费与收入两条业务角色记录，但净额与手续费均为零。

## 后果

### 正面影响

- 数据库约束和 Go 领域层共同保护零和、历史链、投影、持有和幂等不变量。
- 钱包可以明确区分已入账余额、两类冻结、信用占用、可消费额度与超限风险。
- API 结算可以在一次 capture 中原子拆分共享者收入和平台手续费，并可按原始参数复算。
- 管理员能够从用户、激励和损失账户追溯操作者、业务引用、前后余额与对手方。

### 负面影响与成本

- 每次写入需要稳定锁顺序、多个不可变事实和同步投影，数据库事务比直接更新余额更复杂。
- 九位定点最终范围仍受 `BIGINT` 限制；任意精度只用于中间计算。
- 当前读模型与数据库强绑定，未来若拆分服务必须重新建立同等强度的原子边界。

### 风险与缓解措施

- **调用方绕过领域服务**：延迟数据库约束在提交时复算交易、投影、持有事件和命令完整性。
- **并发透支或超卖**：按稳定顺序锁定账户和持有，所有业务记录与账本写入共用数据库事务。
- **舍入分歧**：公式 v1 通过跨层测试固定运算顺序、向上取整、极值和溢出行为；未来改变公式必须新建版本而非改写历史。
- **投影漂移**：管理员指标持续展示余额和持有投影差额，任何非零差异视为账本异常。

## 验证方式

- PostgreSQL 集成测试覆盖零和、分录链、精确冲正、双持有、部分 capture/release、split capture、信用冻结、超限、幂等重放与冲突、同一外层事务多笔记账以及并发竞争。
- 原始 SQL 负向测试证明不平衡交易、伪造冲正、孤立 capture、直接投影修改、普通交易使用损失账户和未完成命令不能提交。
- 公式单元测试覆盖不足一纳积分、独立取整、倍率与手续费、`int64` 极值和任意精度中间值。
- HTTP 与浏览器验收覆盖本人钱包、可追溯分录、余额不足恢复入口、管理员指标、信用冻结与账户明细权限。

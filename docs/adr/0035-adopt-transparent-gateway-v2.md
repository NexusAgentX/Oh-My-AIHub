# ADR-0035：网关透明转发、事后记账与按用户按模型路由（第二版）

- 状态：已通过
- 日期：2026-10-11
- 决策者：维护者
- 关联内容：[ADR-0027](archive/0027-adopt-transparent-gateway-with-post-hoc-billing.md)（被本 ADR 取代）、[ADR-0012](0012-adopt-tiered-model-pricing-and-pricing-formula-v2.md)、[ADR-0025](0025-remove-ledger-holds-and-adopt-c2c-escrow-account.md)、[ADR-0030](0030-price-reliable-token-breakdowns.md)、[ADR-0034](0034-adopt-channel-custom-models.md)、[ADR-0036](0036-adopt-credential-startup-check-and-pinned-egress-pool.md)、[ADR-0039](0039-deploy-as-single-instance.md)

## 背景

ADR-0027 确立了网关的形态：透明转发、不预扣、请求结束后一次记账、按用户按模型路由。v0.15.0 上线后，2026-10-11 的网关评审发现几条规则与真实流量不符：

- **首字超时无条件生效**：非流式请求要等上游生成完才回第一个字节，超过首字超时就被判失败、换渠道重跑，还给健康渠道记一次失败。
- **总超时由 HTTP 客户端计时，包含读完响应体**：持续输出超过总超时的长流被切断，记为中断和渠道失败，计费不完整。兜底任务的 61 分钟时限只考虑了单次尝试，多次尝试累加可能超过它，超过后调用被标为中断，计费丢失。
- **客户端中途断开时立刻取消上游**：旁路解析器读不到结尾的用量，OpenAI Chat / Responses 不收费，Anthropic 只收输入。共享者照付上游费用。
- **配错模型名的渠道永不冷却**：上游对未知模型返回 400 时，网关当作请求本身的问题原样返回，不换渠道、不计失败。这个渠道成功率满分，便宜时会吞掉该模型的全部请求。
- **429 不理会 `Retry-After`**：只累计连续失败次数，到阈值后按固定时长冷却。
- **替客户端打开 `include_usage` 会多出一帧**：客户端最后多收到一帧 `choices` 为空的纯用量帧，直接取 `choices[0]` 的客户端会崩溃。
- **候选被跳过时尝试次数不补位**：先截取前若干个候选再逐个占位，占不到槽位的候选被跳过，后面的候选不会补上来。
- **并发透支没有上界**：ADR-0027 只是接受了“并发请求可能透支若干次请求的费用”，没有限制若干是多少。

这些都改变了 ADR-0027 的规则。按 ADR 流程，本 ADR 整体取代 ADR-0027，并把其中未变的规则完整搬过来。

## 决策目标

- 请求体除顶层 `model`（以及 OpenAI Chat 流式的 `stream_options.include_usage`）外，与客户端发送的字节一致；响应原样返回，唯一例外见规则 6。
- 不预扣费，也不让用户为失败买单；每次成功调用至多一笔平衡交易，重复结束不重复记账。
- 并发造成的透支有上界：不超过“账号在途上限 × 单次请求费用”。
- 超时与失败的判定反映渠道的真实状况，不把客户端行为或请求本身的问题记到渠道头上。
- 路由由用户按模型选择，默认简单，高级能力折叠但齐全。
- 热路径不被观测写入阻塞；计费正确性优先。
- 不解决：格式转换；向量、图片、语音与 Realtime；保存正文；多实例；余额与 Key 预算的冻结或预留。

## 候选方案

### 方案一：保留 ADR-0027，只在实现中修补

不新建 ADR，直接改代码。实现会与 ADR-0027 的规则 4、5、8 和“响应全部原样返回”的目标矛盾，违背“已通过的 ADR 不改写结论”。

### 方案二：恢复预扣或冻结来约束透支

重新引入 ADR-0025 删除的持有机制。代价与 ADR-0027 方案一相同，已被否决。

### 方案三：保留事后记账，修订超时、回退与断开规则，用进程内在途上限约束透支（选定）

账本与计费模型不变。在途上限只是进程内计数，不预留余额。

## 决定

采用方案三，固定以下规则。

1. **透明转发**（沿用）：只做四件事。
   - 换鉴权，写回客户端原来的位置：`Authorization: Bearer`、`x-api-key`、`x-goog-api-key` 或 `?key=`。
   - 可选换 User-Agent。
   - 按渠道规则设置或删除请求头。规则不能触碰 `Host`、`Content-Length`、hop-by-hop 头和鉴权头。
   - 把顶层 `model` 换成渠道的上游名称。

   `model` 的替换与 `include_usage` 的补写都是对原字节的词法扫描和拼接，不重新序列化，有模糊测试保证其余字节不变。出站走 [ADR-0036](0036-adopt-credential-startup-check-and-pinned-egress-pool.md) 的固定出站边界，并叠加 `settings.extra_blocked_hosts`。转发时丢弃 Cookie、`X-AIHub-Tag` 与 `X-Forwarded-*` 类头，避免向第三方泄露站内信息与客户端地址。
2. **事前检查**：
   - （沿用）`余额 > −信用额度`，且 Key 的每日、每月、总额预算（Asia/Shanghai 自然日、自然月）未用完才放行，否则返回 402（`insufficient_balance` / `key_budget_exceeded`）。Key 已用额与渠道当日收入从 `calls` 汇总，在进程内缓存，每次记账后增量更新。
   - （新增）每个账号同时在途的调用数不超过平台设置中的上限，超过时以 429 拒绝，不收费。上限由管理员设置，默认 20，0 表示不限。在途从事前检查通过算起，到该调用记账结束为止，包括规则 6 的续读。在途计数是进程内状态，不预留余额。
3. **路由**：
   - （沿用）每个用户对每个模型选择便宜优先（默认）、稳定优先、快速优先或手动排序，可以取消勾选渠道，可以被单把 Key 覆盖。自己的渠道视为 0 价排最前。Responses 请求带 `previous_response_id` 时优先回到上一轮的渠道。自定义模型按名称聚合路由，见 ADR-0034。
   - （沿用）冷却、并发、每分钟请求数与每日收入上限在进程内按渠道维护（单实例，见 ADR-0039）。
   - （新增）上游 429 带 `Retry-After`（秒数或 HTTP 日期）或 `retry-after-ms` 时，立即按该时长冷却渠道，时长限制在 1 秒到该渠道生效的冷却时长之间，不缩短已有的更长冷却。不带这两个头的 429 仍按连续失败计数处理。冷却粒度是整个渠道，不区分模型。
4. **失败就换**：
   - （沿用）尚未向客户端写出任何字节前，以下情况换下一个候选并计渠道失败：连接失败、首字超时（仅流式，见规则 5）、HTTP 5xx/429/401/403/404/405。
   - （新增）非流式请求超过总超时，同样换下一个候选并计渠道失败。
   - （沿用）上游其他 4xx 默认视为请求本身的问题，原样返回，不换渠道、不收费、不计失败。
   - （新增）例外是响应体表明“模型不存在或不可用”的 4xx，视为渠道配置问题：换下一个候选并计失败，错误码为 `upstream_model_unavailable`。判定依据是 OpenAI 形态的 `error.code` 属于模型不存在一类，或 Gemini 的 `error.status` 为 `NOT_FOUND`，或错误消息命中只针对模型的窄匹配。理由：网关已把 `model` 换成渠道配置的上游名，上游说模型不存在，只可能是渠道的问题。
   - （新增）尝试次数按真正发出的尝试计算：候选因并发等运行时限制占不到槽位时跳过，由后面的候选补位，直到达到最多尝试次数。
   - （沿用）首字之后的中断不再换渠道。
5. **超时**（新增）：沿用平台默认与渠道高级设置中的首字超时与总超时，按请求类型区分含义。

   | 情况 | 规则 | 超时后 |
   | --- | --- | --- |
   | 非流式 | 从发出请求到读完响应不超过总超时；首字超时不适用 | 计渠道失败；尚未写出字节，可以回退 |
   | 流式，首字节之前 | 不超过首字超时 | 计渠道失败；可以回退 |
   | 流式，首字节之后 | 相邻两次读到数据的间隔不超过总超时（空闲超时） | 尝试中断，计渠道失败，按已读到的用量记账 |
   | 任何调用 | 从调用开始最长 60 分钟，包括全部尝试与规则 6 的续读 | 调用中断，不计渠道失败，按已读到的用量记账 |

   超时在请求的 context 上实现，不依赖 HTTP 客户端的整体超时，这样出站连接才能跨请求复用（ADR-0036）。
6. **回写、旁路读用量与客户端断开**：
   - （沿用）响应逐块写回并 flush，同时用有界的旁路解析器读取四种格式的用量。解析器不校验形状，解析失败不影响返回。读不到用量就记为 `succeeded_unbilled`，不记账。上游输出后中断时，按已读到的用量记账，读不到则不收费。
   - （新增）客户端在网关开始回写之后断开：停止写客户端，继续读上游，读到的内容只喂给旁路解析器，按读到的用量记账。上游结束、读满 10 秒、空闲超时或调用上限，四者先到为准，然后取消上游。续读期间上游出错不计渠道失败，客户端断开本身也不计。
   - （沿用）客户端在开始回写之前断开（包括正在等非流式响应或正在回退）：立即取消上游，不收费。
   - （新增，“响应原样返回”的唯一例外）网关替客户端打开 `include_usage` 时（客户端原本没有写 `include_usage: true`），OpenAI Chat 流式响应中 `choices` 为空、只带 `usage` 的那一帧不写给客户端。旁路解析器仍然读取上游的全部字节，计费不受影响。其他字节、客户端自己打开 `include_usage` 的响应、其他三种格式，一律原样返回。
7. **事后记账**（沿用）：
   - 请求结束后，在一个事务内更新 `calls` 并调用账本 `Post`（幂等键 `call:<id>`）：消费者 −(费用 + 手续费)，共享者 +费用，`platform_revenue` +手续费。
   - 价格按请求开始时刻与输入侧 token 选档（ADR-0012、ADR-0030），费用与手续费分别向上取整。
   - `calls` 只在仍为 `in_progress` 时被更新，因此重复结束不会重复记账。
   - **自己的渠道**：手续费为 0，消费者与共享者是同一个账本账户，净额为 0。账本不允许同一账户在一笔交易中出现两次，也不允许零金额分录，所以这类调用不产生账本交易。`calls` 仍记录费用，以 `ledger_tx_id` 为空表示没有交易。
8. **记账失败的兜底**（沿用）：先尝试连同记账一起提交；失败则记录错误日志，只关闭调用（费用已写入、`ledger_tx_id` 为空），由核对与补记（同一幂等键）找出。
9. **崩溃兜底**：后台任务把超过 61 分钟仍为 `in_progress` 的调用标记为 `interrupted`，不收费。61 分钟是调用级上限 60 分钟加 1 分钟余量（时限依据相对 ADR-0027 有变化）。进程在流式响应中途崩溃会丢失这次计费，已接受。
10. **观测与错误**（沿用）：
    - 每次调用有请求 ID（响应头 `X-AIHub-Request-Id`）、尝试时间线、首字时间、输出速度和 token 间隔 p50/p95。
    - 进程内事件总线非阻塞地发布调用与渠道事件，满了就丢弃。
    - 每个请求一行 `slog` JSON，不含正文与任何 Key。
    - 网关自己产生的错误按客户端协议返回官方 SDK 能解析的格式，其中带请求 ID 与平台错误码；上游错误原样透传。

## 后果

### 正面影响

- 一次调用只有 `calls` 一行和至多一笔账本交易；预授权、冻结与补偿状态机保持删除。
- 用户可见的行为简单：余额够就用，失败不收费，路由由自己选。
- 非流式长请求与持续输出的长流不再被误判失败，渠道健康统计更准。
- 断开后续读让主流客户端中途断开时也能按真实用量收费，共享者少白付上游费用。
- 配错模型名的渠道会被回退并冷却，不再吞掉请求。
- 并发透支有明确上界。
- 替客户端打开 usage 不再破坏客户端的解析。

### 负面影响与成本

- 透支仍可能发生，上界约为“在途上限 × 单次请求费用”；已接受，由管理员“需要处理”提示兜底。
- 进程崩溃会丢失在途流式调用的计费；已接受。
- 续读最多 10 秒，期间继续占用渠道并发槽位与账号在途名额。
- 续读 10 秒仍拿不到用量时，仍会少收或不收。是否按已转发内容估算输出 token，待定。
- 自己渠道的调用没有账本交易，“成功调用都有记账”的核对须排除它们。
- 冷却、限额、在途计数和连续失败计数只在进程内，重启后清零，不支持多实例（ADR-0039）。
- “模型不存在”的识别依赖上游错误体；窄匹配可能漏判，漏判时行为与 ADR-0027 相同。
- 去掉纯用量帧需要按 SSE 事件边界缓冲，单个事件要等到边界才写出。

### 风险与缓解措施

- **旁路解析器读不到用量**（非标准 SSE 或压缩响应）：按未计费处理，在调用记录上留下 `succeeded_unbilled` 供查看。
- **字节级 `model` 替换遇到转义与嵌套同名键**：单元测试与模糊测试覆盖，顶层重复键全部替换。
- **把客户端的错误误判为渠道问题**：只看错误码与只针对模型的窄正则；用反例测试（`max_tokens` 过大、消息格式错误等 400）保证它们仍然透传、不计失败。
- **SSE 事件过滤破坏字节**：切分器有模糊测试；不完整的事件先暂存，读到结束时剩余字节原样写出。
- **`Retry-After` 过大让渠道长期不可用**：冷却时长不超过该渠道生效的冷却时长。

### 验证

- 单元与模糊测试：请求体扫描与拼接、SSE 事件切分、四种格式的用量解析、路由排序与尝试补位、冷却（含 `Retry-After` 解析与范围限制）、限额、预算缓存、在途上限、失败分类、请求头与 URL 构造。
- PostgreSQL 集成测试，沿用 ADR-0027 的项目：四种格式流式与非流式经模拟上游字节一致、用量与费用、回退、普通 4xx 不回退、冷却、预算与余额拦截、透支一次后被拦、自己渠道净额 0、重复结束不重复记账、读不到用量不收费、粘性路由、请求头规则与 UA、日志不含正文与 Key。
- PostgreSQL 集成测试，新增项目：非流式超过首字超时仍成功、流式空闲超时、非流式总超时回退、调用级上限、断开后续读计费、“模型不存在”类 4xx 回退及其反例、429 `Retry-After` 冷却、尝试补位、纯用量帧过滤、在途上限拒绝。

## 替代关系

取代 [ADR-0027](archive/0027-adopt-transparent-gateway-with-post-hoc-billing.md)。相对 ADR-0027 的变化见各规则中标为“新增”的条目，以及规则 9 的时限依据；其余规则沿用。

规则 4、6 的“上游错误原样返回”已由 [ADR-0041](0041-redact-channel-key-in-upstream-errors.md) 部分取代：上游错误响应的响应体与响应头值里出现的渠道上游 Key 会被替换为 `[redacted]`，其余仍原样返回；成功响应不受影响。

[ADR-0043](0043-track-background-responses-and-component-billing.md) 细化后台 Responses 的结算点与规则 9 的崩溃兜底：已经登记的后台任务恢复跟踪后在终态关闭，普通调用的规则不变。

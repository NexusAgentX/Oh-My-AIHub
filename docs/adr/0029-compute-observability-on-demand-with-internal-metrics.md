# ADR-0029：观测现算不存快照，指标走内网端口

- 状态：已通过
- 日期：2026-10-08
- 决策者：项目维护者与 AI 产品团队
- 关联内容：[Epic #170](https://github.com/NexusAgentX/Oh-My-AIHub/issues/170)、[Feature #176](https://github.com/NexusAgentX/Oh-My-AIHub/issues/176)、[ADR-0025](0025-remove-ledger-holds-and-adopt-c2c-escrow-account.md)、[ADR-0027](0027-adopt-transparent-gateway-with-post-hoc-billing.md)

## 背景

v0.6.0 的运营台靠巡检表、投影和历史快照回答“账平不平、哪里出了问题”，复杂度和一致性风险都很高。重写后账本只有分录与交易（ADR-0025），网关把每次调用写成一行 `calls`（ADR-0027）。Feature G 需要让每次调用、每一分积分都说得清，同时提供 Prometheus 指标，并且不能因此引入新的状态来源。

## 决策目标

- 调用与积分的每个观测数字都能从 `calls`、账本与 C2C 表直接复算。
- 核对结果不依赖上一次运行的状态，不存历史。
- 指标可被内部监控抓取，但不能经公网入口访问，也不暴露用户或 Key。
- 不解决：OpenTelemetry、推送告警、观测数据的长期留存。

## 候选方案

### 方案一：定时任务写快照与巡检表

查询快，但引入第二份事实来源，快照与账本可能不一致，需要补偿与迁移。

### 方案二：全部现算

没有额外状态；代价是聚合查询随调用量增长变慢，用索引、有限时间窗和一致的只读快照控制。

### 方案三：现算，再叠加进程内缓存

在方案二基础上缓存汇总。当前规模下收益不足，先不引入。

## 决定

采用方案二。

1. 观测查询都是只读 SQL，现算自 `calls`、`ledger_*`、`c2c_*`。余额类汇总由分录求和得到，`balance_nano` 与分录的一致性作为独立核对 ②，因此用户的期初 + 各类变动 = 期末在构造上成立。需要同一状态的查询在一个 `REPEATABLE READ` 只读事务内完成。
2. 五项核对（账户合计为 0、余额等于分录、托管等于卖单未完成量、应计费成功调用都有账本交易、放行交易都有账本交易）每次请求现算；自己的渠道调用按 ADR-0027 不产生账本交易，漏记核对与补记排除它们。
3. 实时流与调用类指标订阅网关的进程内事件总线并读出完整调用；总线对慢消费者丢弃事件而不阻塞网关，因此二者是尽力而为，账务以数据库为准。
4. Prometheus 使用 `prometheus/client_golang`（Prometheus 抓取格式的事实标准实现，自写文本格式与直方图没有收益），监听独立端口 `METRICS_ADDR`（默认 `:9090`），Compose 只 `expose`、不发布，Nginx 不代理。指标不带用户、账户或 Key 标签；`model` 标签限定在目录内，其余为 `other`。
5. 上游原始错误文本只保留 30 天，后台任务每天清空更早调用的 `error_message`，保留状态码与错误码。

## 后果

### 正面影响

- 没有快照、巡检表和补偿逻辑，账本与观测不会分叉。
- 核对结果永远反映当下，历史问题靠审计与调用记录追溯。

### 负面影响与成本

- 管理员积分页与概览每次请求都扫描账户与分录，数据量大后会变慢；需要索引与时间窗，必要时再加缓存（方案三）。
- 新增一个依赖 `prometheus/client_golang` 及其传递依赖。

### 风险与缓解措施

- 指标端口被误暴露：Compose 不发布端口，`SECURITY.md` 要求非 Compose 部署用防火墙或回环地址保证内网。
- 事件被丢弃使指标和实时流偏低：文档注明尽力而为，对账以数据库为准。

## 验证方式

- PostgreSQL 集成测试覆盖：筛选与汇总、受限视图、对账等式、人为制造的不一致逐项被核对发现、补记幂等、CSV 内容、指标包含核心系列且无用户标签。
- 契约测试与集成测试用 `openapi.yaml` 校验每个真实响应。

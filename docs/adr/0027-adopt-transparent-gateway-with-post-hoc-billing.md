# ADR-0027：网关透明转发、事后记账与按用户按模型路由

- 状态：已通过
- 日期：2026-10-08
- 决策者：项目维护者与 AI 产品团队
- 关联内容：[Epic #170](https://github.com/NexusAgentX/Oh-My-AIHub/issues/170)、[Feature #172](https://github.com/NexusAgentX/Oh-My-AIHub/issues/172)、[ADR-0009](0009-adopt-encrypted-upstream-credentials-and-pinned-egress.md)、[ADR-0012](0012-adopt-tiered-model-pricing-and-pricing-formula-v2.md)、[ADR-0025](0025-remove-ledger-holds-and-adopt-c2c-escrow-account.md)

## 背景

v0.6.0 的网关围绕“预授权上限 → 冻结 → 交付 → 结算/补偿”的状态机构建（ADR-0010、ADR-0014、ADR-0016）：每次调用先按目录最坏组合冻结积分，路由按“模型 + 格式”的路由池和备用顺序固定，调用候选、尝试、结算和补偿各有一张表。它保证了不超额，但也带来大量只为预授权服务的机制，并让用户难以理解为什么一次调用被拒、被换渠道或被扣费。ADR-0014 与 ADR-0016 已经把请求/响应形状校验从网关移走，剩下的复杂度主要来自预授权本身。

2026-10-08 的重写（Epic #170）确认：不预扣、不冻结；账本没有持有（ADR-0025）；网关只做透明转发，失败不收费。

## 决策目标

- 请求体除顶层 `model`（及 OpenAI Chat 流式的 `stream_options.include_usage`）外与客户端发送的字节一致；响应全部原样返回。
- 不预扣费也不让用户为失败买单；每次成功调用恰好一笔平衡交易，重复结束不重复记账。
- 路由由用户按模型选择，默认简单、高级能力折叠但齐全。
- 热路径不被观测写入阻塞；计费正确性优先。
- 不解决：格式转换、向量/图片/语音/Realtime、保存正文、多实例。

## 候选方案

### 方案一：保留预授权与冻结，仅简化路由

保证单次请求不超额，但保留冻结、补偿和投影，复杂度不变，也无法解释“为什么被冻结”。

### 方案二：事前只检查余额与预算，事后一次记账

不预扣，允许单次请求透支一点；请求结束后在同一事务内更新调用并过账。并发请求在信用额度边缘可能多透支若干次请求的费用。

## 决定

采用方案二，并固定以下规则。

1. **透明转发**：只做四件事——换鉴权（写回客户端原来的位置：`Authorization: Bearer`、`x-api-key`、`x-goog-api-key` 或 `?key=`）、可选换 User-Agent、按渠道规则设置/删除请求头、把顶层 `model` 换成渠道的上游名称。`model` 的替换与 `include_usage` 的补写都是对原字节的词法扫描和拼接，不重新序列化；有模糊测试保证其余字节不变。出站仍走 ADR-0009 的固定出站边界，并叠加 `settings.extra_blocked_hosts`。请求头规则不能触碰 `Host`、`Content-Length`、hop-by-hop 头和鉴权头。转发时丢弃 Cookie、`X-AIHub-Tag` 与 `X-Forwarded-*` 类头，避免向第三方泄露站内信息与客户端地址。
2. **事前检查**：`余额 > −信用额度` 且 Key 的每日/每月/总额预算（Asia/Shanghai 自然日/月）未用完才放行；否则 402（`insufficient_balance` / `key_budget_exceeded`）。Key 已用额与渠道当日收入从 `calls` 汇总并在进程内缓存，每次记账后增量更新。
3. **路由**：每个用户对每个模型选择便宜优先（默认）/稳定优先/快速优先/手动排序，可取消勾选渠道，可被单把 Key 覆盖。自己的渠道视为 0 价排最前；Responses 请求带 `previous_response_id` 时优先回到上一轮的渠道。冷却、并发、每分钟请求数与每日收入上限在进程内按渠道维护（单实例）。
4. **失败就换**：在尚未向客户端写出任何字节前，连接失败、首字超时、HTTP 5xx/429/401/403/404/405 都换下一个候选；其他 4xx 视为请求本身的问题，原样返回，不换渠道、不收费。首字之后的中断不再换渠道。
5. **旁路读用量**：响应逐块原样写回并 flush，同时用有界的旁路解析器读取四种格式的用量，不校验形状，解析失败不影响返回。读不到用量则 `succeeded_unbilled`，不记账；客户端中途断开或上游输出后中断时，按已读到的用量记账，读不到则不收费。
6. **事后记账**：请求结束后，在一个事务内更新 `calls` 并调用账本 `Post`（幂等键 `call:<id>`）：消费者 −(费用 + 手续费)，共享者 +费用，`platform_revenue` +手续费。价格按请求开始时刻与输入侧 token 选档（ADR-0012），费用与手续费分别向上取整。`calls` 仅在仍为 `in_progress` 时被更新，因此重复结束不会重复记账。**自己的渠道**手续费为 0，消费者与共享者是同一个账本账户，净额为 0，账本不允许同一账户在一笔交易中出现两次，也不允许零金额分录，因此这类调用不产生账本交易，`calls` 仍记录费用并以 `ledger_tx_id` 为空表示无交易。
7. **记账失败的兜底**：先尝试连同记账一起提交；失败则记录错误日志，并仅关闭调用（费用已写入、`ledger_tx_id` 为空），供 Feature G 的核对与补记（同一幂等键）找出。
8. **崩溃兜底**：后台任务把超过一小时零一分钟（单渠道总超时上限加余量）仍为 `in_progress` 的调用标记为 `interrupted`，不收费。进程在流式响应中途崩溃会丢失这次计费，已接受。
9. **观测**：每次调用有请求 ID（响应头 `X-AIHub-Request-Id`，平台错误正文含 `request_id`）、尝试时间线、首字时间、输出速度和 token 间隔 p50/p95；进程内事件总线非阻塞发布调用与渠道事件，满了丢弃；每个请求一行 `slog` JSON，不含正文与任何 Key。

## 后果

### 正面影响

- 删除预授权、冻结、候选/尝试/结算/补偿表与状态机；一次调用只有 `calls` 一行和至多一笔账本交易。
- 用户可见的行为简单：余额够就用，失败不收费，路由由自己选。
- 计费与交付解耦的方向（ADR-0014、ADR-0016）完整落地。

### 负面影响与成本

- 并发请求在无预扣下可能让单个账号透支超过信用额度若干次请求的费用；已接受，由管理员“需要处理”提示。
- 进程崩溃会丢失在途流式调用的计费；已接受。
- 自己渠道的调用没有账本交易，Feature G 的“成功调用都有记账”核对须排除它们。
- 冷却、限额和连续失败计数只在进程内，重启后清零，不支持多实例。

### 风险与缓解措施

- 旁路解析器遇到非标准 SSE 或压缩响应时读不到用量：按未计费处理，并在调用记录上留下 `succeeded_unbilled` 供查看。
- 字节级 `model` 替换的转义与嵌套同名键：单元测试与模糊测试覆盖，顶层重复键全部替换。

## 验证方式

- 单元与模糊测试：请求体扫描与拼接、四种格式用量解析、路由排序、冷却/限额/预算缓存、请求头与 URL 构造。
- PostgreSQL 集成测试：四种格式流式与非流式经模拟上游字节一致、用量与费用、回退、4xx 不回退、冷却、预算与余额拦截、透支一次后被拦、自己渠道净额 0、重复结束不重复记账、读不到用量不收费、粘性路由、请求头规则与 UA、日志不含正文与 Key。

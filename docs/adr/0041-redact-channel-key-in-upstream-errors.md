# ADR-0041：上游错误体返回前抹掉渠道 Key

- 状态：已通过
- 日期：2026-10-11
- 决策者：维护者（授权协调者夜间推进）
- 关联内容：[ADR-0035](0035-adopt-transparent-gateway-v2.md)、[ADR-0036](0036-adopt-credential-startup-check-and-pinned-egress-pool.md)

## 背景

网关把上游的非 2xx 响应缓冲（最多 1 MiB）后交给客户端，有两条路径：请求本身的 4xx 直接透传（ADR-0035 规则 4），以及所有候选都失败时返回最后一个上游的应答。ADR-0035 的目标和规则 6 写的是“响应原样返回”，唯一例外是替客户端开启 usage 时去掉纯用量帧。

调用方是消费者，不是渠道主。有些中转站拒绝请求时会把收到的凭据写进错误信息：“Incorrect API key provided: sk-…”、回显请求头或请求 URL（Gemini 的 `?key=`）。原样透传后，消费者就能读到渠道主的上游 Key，违反 ADR-0036 决定 1“上游 Key 不通过任何接口回显”。

日志和 `calls` 里存的错误文本早已先经过 `scrub`（Key 换成 `***`），只有回给客户端的字节没有。Key 在上游错误里的写法也不止原样：JSON 编码器可能把斜杠写成 `\/`、把字符写成 `\uXXXX`，URL 里是百分号编码。

## 候选方案

### 方案一：原样透传（现状）

最简单，错误信息完整。渠道上游一旦回显 Key，泄露给每个消费者。

### 方案二：抹掉渠道 Key（选定）

返回给客户端之前，把本次尝试使用的渠道 Key 的出现替换为固定占位。上游的状态码和错误信息保留，客户端仍能区分原因、SDK 仍能解析；Key 没有出现时字节不变。

### 方案三：完全不返回上游错误体

改成网关自己的错误（状态码加通用文案）。最稳妥，但丢掉上游给出的原因：`max_tokens` 过大、消息格式错误这类请求自身的问题，用户要靠上游的说明去改；也违背透明转发，客户端对上游错误体格式的依赖会失效。

## 决定

采用方案二。

1. **范围**：网关缓冲的全部上游非 2xx 应答，即请求自身的 4xx 透传，以及换渠道时保留下来、最后返回的失败应答（429、5xx、因“模型不可用”回退的 4xx 等）。只替换本次尝试使用的那个渠道的 Key。
2. **替换什么**：响应体和响应头值里的三类写法，精确匹配、不做模式猜测：
   - Key 原样；
   - Key 的百分号编码（查询与路径两种）；
   - 写在 JSON 字符串里的任意转义形式：`\/`、`\"`、`\\`、`\uXXXX`（大小写与代理对均可），不限于某个编码器的习惯。

   被上游掩码或截断的 Key（如 `sk-…abcd`）不是这个 Key，不识别。
3. **占位**：`[redacted]`。日志与存储的错误文本沿用 `***`，由同一匹配逻辑处理，因此也同样覆盖这些写法。
4. **其余不变**：Key 没有出现时，状态码、响应头、响应体字节与上游一致。出现时只替换匹配的片段，`Content-Length` 改为实际写出的长度，原本担保这些字节的 `Content-MD5`、`Digest`、`Content-Digest`、`Repr-Digest` 去掉。
5. **1 MiB 上限**：先多读 Key 最长编码形式（Key 长度的 18 倍）的余量，替换之后再截到 1 MiB，使跨越上限的 Key 不会在末尾留下开头。
6. **无法检查的编码体**：传输层没有解码的错误体（上游带了不是 `identity` 的 `Content-Encoding`；网关只声明 gzip，传输层会解码，合规上游不会发出别的编码）无法查找 Key，不返回正文。状态码和其他响应头保留，去掉 `Content-Encoding`，上游给了 `Content-Length` 的改为 0。
7. **成功响应不处理**，非流式和流式都按 ADR-0035 规则 6 原样返回。理由：
   - 回显发生在拒绝请求的错误路径，错误处理代码把请求上下文写进消息。Key 只出现在请求的鉴权位置，不在提示词里，模型输出里不会有它，成功路径没有已知的回显机会。
   - 成功响应不缓冲，边读边写并旁路解析用量。要可靠抹掉，就得在块与块之间持有一个 Key 编码长度的尾部（给每个流式帧增加延迟），或缓冲整个响应体（推迟首字节，并与断开后续读冲突）；上游的 `Content-Length` 也已先写出。代价和收益不相称。
   - 若发现某个上游在成功响应里回显 Key，说明它在向任何调用方泄露凭据，应由渠道主换 Key、停用该渠道；届时再另立决定。

## 后果

### 正面影响

- 消费者不能再借上游的错误回显得到渠道主的上游 Key；ADR-0036 决定 1 在网关的错误透传上成立。
- 上游的状态码和错误信息保留，对没有回显 Key 的错误，行为与 ADR-0035 完全一致。
- 日志与存储的错误文本因共用匹配逻辑，覆盖面同步扩大。

### 负面影响与成本

- 上游错误不再绝对“原样”：Key 出现处会变成 `[redacted]`。Key 过短（例如只有一两个字符）时，正文里相同的字符也会被替换；真实的 Key 不会这样短。
- 变形后的 Key（base64、哈希、大小写变换、HTML 实体）、被掩码或截断的 Key 不识别。
- 成功响应不处理，见决定 7。
- 传输层没有解码的编码错误体不再返回正文，消费者拿不到这条上游错误的说明，只有状态码。
- 读取错误体最多多读 Key 长度的 18 倍（Key 最长 8192 字节时约 144 KiB），仅在上游返回错误时发生。

### 风险与缓解措施

- **替换破坏 JSON**：占位 `[redacted]` 不含引号和反斜杠，替换发生在字符串内部时 JSON 仍合法；测试用多种 JSON 编码器（含 PHP 式的 `\/`、全部 `\u` 转义）验证。
- **误伤**：只精确匹配本次尝试的 Key，不按“像 Key 的字符串”猜测。
- **响应头不再匹配响应体**：`Content-Length` 与摘要类头随正文调整或去掉。

### 验证

- 单元测试：各种写法的匹配、没有 Key 时同一份字节、响应头、`Content-Length`、1 MiB 边界、编码体、日志与存储文本的 `scrub`；模糊测试保证替换后不留下原样出现的 Key。
- PostgreSQL 集成测试：四种格式的 400、401、500、502 错误体与响应头中的回显（含转义的斜杠和 `?key=` 查询）、所有候选失败、没有 Key 时字节不变、日志与存储的错误文本仍被抹掉。

## 替代关系

部分取代 [ADR-0035](0035-adopt-transparent-gateway-v2.md) 规则 4、6 中“上游错误原样返回”：响应体和响应头值中出现的渠道上游 Key 会被替换，其余仍原样返回。ADR-0035 的其他规则不变。

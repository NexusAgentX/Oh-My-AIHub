# ADR-0040：网关热路径的只读数据来自进程内快照，写后同步失效

- 状态：已通过
- 日期：2026-10-11
- 决策者：维护者
- 关联内容：Epic #360（高性能网关）、Issue #365（G8.1）、[ADR-0035](0035-adopt-transparent-gateway-v2.md)、[ADR-0036](0036-adopt-credential-startup-check-and-pinned-egress-pool.md)、[ADR-0039](0039-deploy-as-single-instance.md)

## 背景

网关性能基线（Epic #360、Issue #361）测得，一个成功的请求要向数据库发 21 条语句，其中在访问上游之前的读取占了大半：按摘要查 Key、读目录模型和它的价格档（两条）、解析路由偏好（账号级与 Key 级各两条）、读候选渠道。这些数据只有管理员、渠道主和用户在后台操作时才会变，一天里几乎不变，却在每个请求里重读一遍，每次一个数据库往返。

ADR-0039 已经定下按单实例部署，并写明“后端是唯一写入数据库的进程，所以缓存在写事务提交后于进程内失效，另以定期全量刷新兜底”。本 ADR 把这条原则落实到网关读取的数据上，并规定它的边界：哪些数据、怎样失效、哪些失效必须在管理操作返回前完成。

约束：

- 停用或删除 Key、停用账号、下架或删除渠道，是安全相关的操作：管理员点下之后，下一个请求就不能再用被停用的 Key，也不能再选到被下架的渠道。缓存不能让这些操作“最多晚几秒生效”。
- 计费不能变：请求按开始时刻的价格与渠道结算，价格变更在写操作返回后对之后的请求生效。
- 不引入新的外部组件（ADR-0006、ADR-0039）。

## 候选方案

### 方案一：每次请求查库（现状）

最简单，永远是最新的。每个请求多十来个往返，数据库连接与延迟都被只读数据占着。

### 方案二：按需加载的缓存，条目带有效期

Key、模型、候选各自在第一次读到时加载，过期后重读。实现小，但：

- 停用 Key 要等有效期结束才生效，与上面的安全约束冲突；缩短有效期就退回到方案一。
- 查不到的 Key 只能回落到数据库确认，任何人用随机 Key 就能把请求打到数据库，或者把缓存撑满。

### 方案三：全量快照，写事务提交后同步重建，另有定期全量重建兜底（选定）

热路径读取的数据整体放进内存，作为不可变的快照整体替换。后端是唯一写入进程，每条写路径在事务提交成功之后通知缓存，缓存重建受影响的快照，之后写操作才返回。每 60 秒再整体重建一次，防止漏掉的写入长期不可见。

### 方案四：PostgreSQL `LISTEN/NOTIFY` 或外部缓存

用于多实例：写入方发通知，各实例收到后失效。通知是异步的，“返回前已生效”的保证做不到；单实例下也用不上。ADR-0039 把多实例列为重新评估的条件，届时再决定。

## 决定

采用方案三。

1. **进入快照的数据**（`internal/snapshot`）：
   - **Key**：按摘要的全量映射，含启用状态、过期时间、别名、允许的模型、预算，以及所属账号是否正常。
   - **模型目录**：全部模型（停用的也在，网关自己返回“模型不存在或未启用”），含币种、四个基准价、细分价与条件价格档。
   - **渠道候选**：由渠道、渠道模型与所有者状态构建的“(模型, 格式) → 候选”索引，条件与顺序同原来的候选查询（渠道上架、未删除、所有者正常；渠道模型启用、未待设倍率；按渠道 ID 排序）；含自定义模型（ADR-0034）和渠道的高级设置、加密的上游凭据。同一份数据导出各格式下在线的模型（`/v1/models`）和自定义模型是否在线。
   - **路由偏好**：Key 级、账号级两层的全部已存偏好及其渠道列表；没有记录即默认偏好。
   - **Responses 粘性**：最近的“response_id → 渠道”小 LRU（1 万条），由调用结算时写入；未命中再查库。
   - 不进快照：余额与信用额度、渠道统计、平台设置（本来就有 5 秒的快照；美元汇率在请求时从设置快照应用，不烙进候选）、解密后的凭据。它们由各自的后续决定处理。
2. **读规则**：
   - 快照里没有的 Key 就是无效 Key，直接拒绝，不回落到数据库。全量快照里没有它，数据库里也没有它；刚创建的 Key 靠规则 3 保证已在快照里。
   - 快照里的值被所有请求共享，调用方只读。需要修改的（引擎给候选设置汇率）拿到的是副本。
3. **失效规则**：
   - 每条写路径在事务提交成功之后调用缓存，缓存重建受影响的快照，**重建完成后写操作才返回**。所以对网关的下一个请求来说，所有后台操作都是“返回即生效”，不分安全相关与否；安全相关的四类（停用或删除 Key、停用账号、下架或删除渠道，含管理员强制下架）因此不需要特殊路径。
   - 每个快照记录自己已经计入多少次变更。重建在开始前读取这个计数，它的查询发生在计数之后，必然看到计数内的全部提交。读取时若快照比最近一次计数的变更旧，不使用它：立即重建，重建失败则这次请求报错（失败关闭），不给出旧答案。
   - 并发的失效合并成少数几次重建；重建与写者的请求上下文脱钩，客户端在提交后断开不会让快照落后。
   - 写失败（事务回滚）不失效。例外：路由偏好的保存在提交之后还要读回，读回失败时也失效。
4. **兜底**：
   - 启动时加载一次，读不到就拒绝启动。
   - 之后每 60 秒全量重建。失败时保留上一份快照并记录日志（已被计数变更作废的快照除外，见上）。
   - 不经后台写库的改动（手工 SQL、迁移）最长 60 秒后可见。
5. **接入方式**：
   - 缓存层在引擎已有的接口之后：`gateway.Store`（Key、候选、在线模型、Responses 粘性）、`routing.Store`（偏好解析）、`gateway.Models`（目录读取）。引擎只需要把目录依赖从具体类型改为接口。
   - 写路径的钩子是对领域 Store 接口的包装（Key、渠道、目录、路由、身份），由组合根 `postgres.Cached` 提供，`cmd/server` 与测试环境用它构建所有会写这些数据的服务。
   - 每个被包装的接口，其全部方法都必须在清单里归类为“写，使哪些快照失效”或“不改变快照里的数据”。守护测试在接口新增方法而清单没有时失败，写方法漏接钩子时也失败。
6. **不变量**：
   - 计费按请求开始时读到的价格、倍率与候选，与原来一致。
   - 进行中的请求不受之后的变更影响（包括已经选定的渠道、已经读到的 Key）。
   - 余额、冷却、并发等运行时状态不在快照里，仍按原有方式实时判断。

## 后果

### 正面影响

- 每个请求在访问上游之前不再向数据库发读语句（余额读取除外，见 Epic #360 的 G8.2）。数据库往返与连接占用相应减少，网关自增延迟降低。
- 所有后台操作返回即生效，不是“最多晚几秒”的 TTL 语义；安全相关的操作不需要单独的路径。
- 无效 Key 不能把请求打到数据库。

### 负面影响与成本

- 内存随 Key 数量与渠道模型数量线性增长。现有规模（邀请制，每人最多 20 把 Key）下是兆字节级。
- 后台写操作多一次重建：它是对相应表的一次全量读，当前规模下是毫秒级。写操作很少，每次重建的成本由发起写操作的管理员或用户承担，不落在网关请求上。若 Key 与渠道增长到全量重建成为负担，改为按行增量更新，不改外部行为。
- 绑定单实例（ADR-0039）。多个后端副本时，一个副本的写操作无法使另一个副本的快照失效；将来做多实例，需要改用 PostgreSQL `LISTEN/NOTIFY` 并重新评估“返回前生效”的做法。
- 新增会写这些数据的路径，必须经过包装的 Store 并归类；绕过它（例如服务直接持有裸 Store）会让改动最长 60 秒后才可见。

### 风险与缓解措施

- **漏接写路径**：清单与守护测试；每类写路径各有“下一个请求立即反映”的集成测试；60 秒全量重建兜底。
- **快照与数据库不一致**：集成测试用同一数据集比较快照与数据库查询的结果（候选、在线模型、自定义模型、Key、路由解析、目录），分别比较从零构建的快照与经历了整个构建过程中每次失效的快照。
- **重建期间读取被拖慢**：只有被作废的快照才让读取等待，等到的是一次全量读，之后所有读取又是无锁的指针读取。
- **数据库故障时的行为**：已作废的快照失败关闭，请求得到内部错误；没有被作废的快照继续服务到下一次兜底重建，与网关此时本来也无法开调用记录一致。

### 验证

- 单元测试：快照构建（索引、顺序、格式展开、在线模型）、失效后重建、进行中的重建不覆盖之后的变更、并发合并、读取者不会看到被撤销的变更、失败关闭、60 秒兜底、粘性 LRU、写方法清单。
- PostgreSQL 集成测试：快照与数据库逐项等价；停用或删除 Key、停用账号及其渠道、渠道下架、强制下架与恢复、删除，管理操作返回后下一个请求立即拒绝或不再选中；新建 Key 与惰性创建的默认 Key 立即可用；模型价格、启停、删除，渠道倍率、格式、上游名、凭据、地址、高级设置，Key 的允许模型、别名、过期、预算，路由偏好，`/v1/models` 都在下一个请求反映；并发读写下的 Key 开关；手工 SQL 在兜底重建后可见；稳态下每个请求不再读取快照里的数据。
- 性能：用基线工具（`docs/runbooks/gateway-baseline.md`）对比合并前后的语句数、延迟与 CPU，结果写在 Issue 与 PR。

## 替代关系

无。本 ADR 落实 ADR-0039 的“以后加入的热路径缓存同样放在进程内”一条，不改变它的结论。

余额缓存（Epic #360 的 G8.2，Issue #369）沿用本决定：账号的余额与信用额度也放在进程内，写事务提交后失效，每 60 秒重新加载，读不到又没有旧值时失败关闭。它不是快照而是按账号惰性加载的缓存，失效挂在账本过账的统一入口上（事务提交、回滚或提交结果不明之后），网关自己的结算在提交后直接累加；实现与规则见 `ARCHITECTURE.md`，不改变本 ADR 的任何结论。

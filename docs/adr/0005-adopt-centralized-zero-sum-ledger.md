# ADR-0005：采用中心化零和复式账本作为积分清算核心

- 状态：已通过
- 日期：2026-09-01
- 决策者：仓库维护者
- 关联内容：[Feature #6](https://github.com/NexusAgentX/Oh-My-AIHub/issues/6)、[Epic #16](https://github.com/NexusAgentX/Oh-My-AIHub/issues/16)、[Feature #18](https://github.com/NexusAgentX/Oh-My-AIHub/issues/18)

## 背景

Oh-My-AIHub 需要在没有预发行积分的情况下，让首个消费者调用共享渠道，并让共享者获得可以继续消费或通过 C2C 转让的积分。平台还需要处理信用额度、API 手续费、冻结、部分成交、自有渠道调用和无法收回的负余额。

若只在用户表中直接增减余额，任何漏记对手方、重复结算、并发竞态或人工修改都会让积分来源无法解释。若预发行积分或采用链上资产，又会引入与小圈子内部清算无关的发行、流动性、基础设施和运维复杂度。

## 决策目标

- 所有积分来源、去向和业务原因都可追溯。
- 从零余额开始，通过受控信用完成冷启动而不预发行积分。
- API 与 C2C 共用一致、原子和可审计的结算基础。
- 支持冻结、手续费、坏账、自有渠道和并发幂等场景。
- 保持中心化小圈子产品的实现与运维简单。

本决策不解决人民币托管、自动做市、链上清算、跨实例结算或信用额度算法。

## 候选方案

### 方案一：直接维护可变余额

每个业务入口直接增加或减少用户余额。实现初期简单，但无法系统保证每次变化都有对手方；审计、回滚、并发、冻结和坏账处理容易形成互不一致的特殊逻辑。

### 方案二：中心化零和复式账本

由平台数据库保存账户、不可变交易和平衡分录。所有用户和系统账户纳入同一恒等式，余额是分录投影或受约束缓存；信用允许账户在下限内为负，正负积分同时产生。

该方案能够使用常规事务数据库保证原子性和一致性，符合中心化单实例边界，但要求所有业务严格通过统一记账接口。

### 方案三：预发行积分或采用链上资产

预先创建积分池，或用区块链发行与转移资产。它能提供另一种资产来源或公开验证方式，但会产生发行分配、链上费用、密钥管理、最终性、流动性和跨系统一致性问题，也与平台不发行、不回购、不做市的产品原则冲突。

## 决定

采用方案二：中心化零和复式账本。

- 每个用户账户以及平台激励、平台损失等系统账户都是账本主体。
- 所有已提交分录的金额总和必须为零；任何不平衡交易不得提交。
- 每个账户初始余额为零。信用额度只定义允许出现的最低余额，不创建独立赠送资产。
- 可用与冻结是同一账户余额的状态划分；冻结和解冻不产生或销毁积分。
- API 消费、手续费、C2C 划转、人工调整和坏账承担都使用统一、原子、幂等的交易入口。
- 自有渠道调用仍产生同一账户的消费借记与渠道收入贷记，手续费为零，保留完整业务记录。
- 负余额不得直接抹除；平台决定承担时，通过平衡交易把负值转入平台损失账户。
- 人民币始终在 C2C 双方之间流转，不进入本账本。
- 平台不发行、销毁、回购或做市积分；一积分约等于一元只作为参考计价单位。

## 后果

### 正面影响

- 任意积分都能回答从何处来、到何处去、为何发生和关联哪项业务。
- 零余额与信用额度可以同时创造相等的正负余额，解决无创世发行的冷启动。
- API 与 C2C 可以复用一致的余额、冻结、幂等和审计机制。
- 全账户余额合计为零成为简单而强力的运行监控与故障信号。
- 平台激励和坏账成本不会隐藏在特殊字段中。

### 负面影响与成本

- 所有业务状态与账本提交必须共享明确的事务边界，实现复杂度高于直接改余额。
- 价格、用量、倍率和手续费需要确定精度、舍入与历史快照规则。
- 冻结、部分成交、重试和并发会要求严格的状态机和幂等设计。
- 用户永久离开时负余额仍存在，或必须由平台损失账户明确承担。

### 风险与缓解措施

- **漏记或重复记账**：数据库约束平衡交易，业务入口强制幂等键，不暴露直接改余额接口。
- **并发超额消费或超卖**：余额、信用、冻结与业务状态在单一事务内锁定和校验。
- **数值误差**：使用确定精度的整数最小单位或定点数，禁止浮点数承担最终结算。
- **历史账单漂移**：调用保存当时的基准价、倍率、手续费率和用量快照。
- **坏账被隐藏**：保留原负余额，或用显式交易转入平台损失账户。
- **账本异常未被发现**：持续监控全账户余额总和，并提供交易与分录审计查询。

## 验证方式

- 单元和集成测试拒绝不平衡交易，并覆盖信用、冻结、解冻、手续费、自有渠道和坏账转移。
- 并发测试证明重复请求、并发消费、并发部分成交和失败回滚不会重复结算或突破可用余额。
- 属性或不变量测试在任意已提交交易序列后验证全账户余额合计为零。
- 管理员不能通过任何正常接口直接修改余额；人工调整也必须产生完整平衡分录。
- 运行指标持续暴露全账户余额总和，非零时进入异常处理。

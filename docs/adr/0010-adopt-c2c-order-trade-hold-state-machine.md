# ADR-0010：采用 C2C 父子持有与订单交易状态机

- 状态：已通过
- 日期：2026-09-02
- 决策者：项目维护者与 AI 产品团队
- 关联内容：Feature #23、[ADR-0008](0008-adopt-immutable-ledger-holds-and-pricing-formula-v1.md)

## 背景

首版 C2C 市场允许买卖双方按固定单价发布买单或卖单，并由其他用户部分成交。人民币在双方选定的外部支付工具中直接流转，平台只托管积分；买家声明付款后，卖家确认到账才释放积分，争议由管理员裁决。

这条流程同时跨越订单剩余量、单笔交易状态、账本持有、部分成交、超时、取消、争议、权限和幂等边界。如果仅在业务表中记录数量，或为每次操作直接修改余额，订单与账本可能在并发下分叉；如果所有订单都采用同一种持有方式，买单又会在尚未选定卖家时错误冻结买家的积分。需要固定一套可由数据库事务证明的状态机和父子持有关系。

## 决策目标

- 卖单发布时即证明全部待售积分可用，部分成交、取消和裁决后不出现超额释放或双花。
- 买单不预先冻结买家的积分，每个接单卖家只为自己的成交数量承担持有。
- 订单数量、交易状态、账本持有和最终划转始终在一个事务中变化。
- 同一命令可安全重试，并发成交、取消、超时、付款和裁决只能产生一个合法终态。
- 账户被停用或冻结后阻止新交易，同时不让已有持有和已付款交易永久滞留。
- 支付方式、联系方式、付款说明、争议陈述和证据图片按最小授权与独立密钥生命周期保护。

本 ADR 不解决外部人民币支付真实性自动验证、自动做市、订单簿撮合、权重调度或平台协议转换。

## 候选方案

### 方案一：每笔成交独立创建持有

卖单发布时只记录业务订单，每次被接单时才为对应交易创建持有。模型简单，但卖家可以在挂单后先消费余额，导致展示中的卖单无法成交；并发接单也需要重复证明总剩余库存，无法满足“挂单即冻结”的产品语义。

### 方案二：卖单使用父持有，部分成交分配给子交易；买单按成交创建持有

卖单发布时创建覆盖总数量的 `asset_reservation` 父持有；每次部分成交把父持有中的可用数量原子分配给交易，取消只释放尚未分配的数量。买单没有父持有，接单卖家为本次成交创建独立 `asset_reservation`。两种订单共享交易状态机与最终 capture/release 路径。

该方案准确表达两种订单的风险承担方，并能复用 ADR-0008 的不可变账本与持有原语，但需要显式维护父单数量恒等式和全局锁序。

### 方案三：只在 C2C 表中维护余额和冻结投影

C2C 自行更新用户余额、冻结量和成交状态。实现表面上直接，但会绕过不可变零和账本、幂等命令、持有事件和投影校验，无法证明每次积分变化都有对手方，因此不采用。

## 决定

采用方案二，并固定以下约束：

1. 卖单创建时以订单 UUID 作为业务标识创建一个只由正余额支持的 `asset_reservation` 父持有。父单始终满足 `total = available + allocated + settled + closed`：
   - 部分成交只把 `available` 转入该交易的 `allocated`；
   - 卖家或管理员取消订单只把当时的 `available` 转入 `closed` 并释放对应父持有数量，已分配交易继续独立完成；
   - 单笔交易释放给买家时把对应数量由 `allocated` 转入 `settled` 并 capture；未结算交易在父单仍开放时只恢复 `available`、不改变父持有，父单已取消时才转入 `closed` 并精确 release。
2. 买单不创建父持有。卖家接单时以交易 UUID 创建覆盖本次成交数量的 `asset_reservation`；释放给买家时 capture，交易取消、超时或退还卖家时始终精确 release，并按父单是否已取消恢复 `available` 或转入 `closed`。capture 或 release 必须使用同一个交易业务标识和精确数量。
3. 每笔交易独立保存不可逆转的状态演进。正常路径是 `awaiting_payment → paid → released`；未付款可取消或超时退回，已付款可以进入 `disputed`，管理员只可将 `paid` 或 `disputed` 裁决为放行买家或退还卖家。以数据库时钟为准，`now >= payment_deadline` 即已到期；在锁内重新判断状态和期限。
4. 每个写命令以“操作 + 操作者 + Idempotency-Key + 实际净化后载荷摘要”唯一识别，首次成功结果保存快照；同载荷永久重放，异载荷冲突。事务先按稳定排序取得涉及账户的 advisory lock，再读取身份、订单、交易和账本持有，避免账户管理与 C2C 的反向锁序。
5. 普通用户被停用、首次改密未完成或信用被冻结后不能建立新的 C2C 风险敞口。管理员或系统可以带必填原因取消挂单尚未分配的部分，也可以直接终结 `paid` 或 `disputed` 交易；这些操作都写入不可变事件，不依赖临时重新启用账户。
6. 公开市场只展示支付方式类型。收款方式详情、联系方式、付款说明、争议陈述和证据使用独立于上游凭据的版本化 AES-256-GCM 密钥环加密，并以用途、记录 ID 和密钥 ID 作为附加认证数据。JPEG/PNG 图片在服务边界解码、限制尺寸、重新编码并重算摘要；终态满 180 天后销毁私密正文和图片密文，保留非敏感审计元数据。
7. 付款截图和陈述只作为人工核实证据，不能触发自动放行。证据下载只允许交易双方和管理员，响应禁止缓存并使用附件语义；任何 API 投影都不得包含 nonce、密文或密钥 ID。

## 后果

### 正面影响

- 卖单库存从发布到终态始终由一个账本父持有担保，部分成交不会超卖。
- 买单只冻结实际接单卖家的积分，不制造无意义的买方资产持有。
- 业务状态、持有事件和零和交易共享事务，能够从不可变事实重建并核对投影。
- 幂等快照和稳定锁序使客户端重试与竞争命令得到确定结果。
- 即使参与者账户随后受限，管理员和系统仍可安全收束已有风险。
- 私密支付资料与渠道凭据采用不同用途的密钥和保留周期，降低跨域泄漏影响。

### 负面影响与成本

- 买卖单采用不同的持有创建时机，服务和测试必须显式覆盖两条路径。
- 父单需要维护四项数量投影，所有成交、取消和裁决都必须在锁内校验恒等式。
- 外部人民币付款仍需交易双方确认或管理员人工裁决，平台不能自动证明到账。
- 密钥轮换、授权下载和 180 天清理任务成为持续运维责任。

### 风险与缓解措施

- 锁顺序回归可能造成死锁：账户管理与 C2C 共用同一账户 advisory lock，集成测试覆盖停用或冻结与成交、取消、放行和退回的竞争。
- 重复或越界命令可能多次改变持有：由幂等载荷摘要、交易业务标识唯一性和账本延迟约束共同拒绝。
- 图片可能携带元数据或解码炸弹：仅接受 JPEG/PNG，限制字节和像素，服务端强制解码重编码，不信任调用者传入的摘要或净化标记。
- 私密字段可能因 DTO 复用泄漏：存储模型与公开、参与者和管理员投影分离，并用 API 泄漏边界测试约束。

## 验证方式

- 在真实 PostgreSQL 上验证卖单父持有、买单成交持有、部分成交、并发吃完最后库存、取消只释放可用量和全局零和一致性。
- 覆盖付款、取消、超时、争议、放行和退回的同态重试、异载荷冲突、精确期限与相互竞争，证明只产生一个终态和一次持有事件。
- 使用 Go race 和真实数据库并发测试覆盖账户停用或信用冻结与成交、取消、capture、release 的锁序。
- 验证支付方式公开投影、参与者私密投影、证据下载授权、图片净化、AEAD 绑定、密钥库存校验与终态 180 天清理。
- 验证桌面、平板和移动端市场、挂单、我的订单、交易详情、争议与管理员裁决流程与 OpenPencil 设计基线一致。

## 替代关系

无。本 ADR 建立在 ADR-0008 的账本与持有决策之上。
